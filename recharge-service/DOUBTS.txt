Question 1: Recharge Status Updates & Payment Flow
Your Question: "Suppose a user initiates recharge, first the status will be marked as failed. But suppose now the page switches to payment service where payment succeeded, so how will the recharge status be changed?"

ANSWER: ❌ Your assumption is incorrect. The status is NOT marked as FAILED first. Here's the actual flow:

Actual Implementation Flow:

// Step 1: Create recharge (INITIATED)
recharge.setStatus(RechargeStatus.INITIATED);
recharge = rechargeRepository.save(recharge);

// Step 2: Update to PROCESSING
recharge.setStatus(RechargeStatus.PROCESSING);
recharge = rechargeRepository.save(recharge);

// Step 3: Call Payment Service SYNCHRONOUSLY (waits for response)
ApiResponse<PaymentResponse> paymentApiResponse = paymentServiceClient.processPayment(paymentRequest);

// Step 4: Update status based on payment result
if (paymentResponse != null && "SUCCESS".equals(paymentResponse.getStatus())) {
    recharge.setStatus(RechargeStatus.SUCCESS);  // ← SUCCESS
    recharge.setTransactionId(paymentResponse.getTransactionId());
} else {
    recharge.setStatus(RechargeStatus.FAILED);  // ← FAILED
    recharge.setFailureReason("Payment failed");
}

// Step 5: Save final status
recharge = rechargeRepository.save(recharge);

// Step 6: Return response to user
return mapToResponse(recharge);
Key Points:

SYNCHRONOUS Payment: Recharge Service WAITS for Payment Service response before updating status
No Page Switch: This is a backend API call, not a page redirect
Single Transaction: Everything happens in one request-response cycle
Status Flow: INITIATED → PROCESSING → SUCCESS/FAILED (never FAILED first)
Timeline:

0ms:    User sends POST /api/recharges
10ms:   Recharge created (INITIATED)
15ms:   Status updated (PROCESSING)
20ms:   Payment Service called
2000ms: Payment Service returns (SUCCESS/FAILED)
2005ms: Recharge status updated (SUCCESS/FAILED)
2010ms: Response sent to user
If Payment is PENDING (Stripe test mode):

Payment Service returns status: "PENDING"
Recharge Service checks: "SUCCESS".equals(paymentResponse.getStatus())
This is FALSE (because status is "PENDING", not "SUCCESS")
Recharge status becomes: FAILED
Failure reason: "Payment failed"
This is a limitation: Current implementation treats PENDING as FAILED. To fix this, you'd need to add:

if ("SUCCESS".equals(paymentResponse.getStatus())) {
    recharge.setStatus(RechargeStatus.SUCCESS);
} else if ("PENDING".equals(paymentResponse.getStatus())) {
    recharge.setStatus(RechargeStatus.PROCESSING);  // Keep as PROCESSING
} else {
    recharge.setStatus(RechargeStatus.FAILED);
}
No changes needed in Payment Service - it already returns the correct status. The issue is in Recharge Service's handling of PENDING status.

Question 2: Purpose of X-User-Id Header
Your Question: "What's the use of X-User-Id when there is no such use of it?"

ANSWER: ✅ X-User-Id is CRITICAL for security and authorization. Here's why:

Purpose 1: User Authorization (Security)

// In RechargeController
@PostMapping
public ResponseEntity<ApiResponse<RechargeResponse>> initiateRecharge(
        @RequestHeader("X-User-Id") Long userId,  // ← Extracted from header
        @RequestBody RechargeRequest request) {
    
    // Uses userId to create recharge for THIS user only
    RechargeResponse response = rechargeService.initiateRecharge(userId, request);
    return ResponseEntity.status(HttpStatus.CREATED).body(ApiResponse.success(...));
}
Without X-User-Id: User could recharge for ANY user (security breach!)

With X-User-Id: User can ONLY recharge for themselves

Purpose 2: Preventing Spoofing

Attack Scenario (without X-User-Id):

POST /api/recharges
Authorization: Bearer <USER_A_TOKEN>
Body: { "userId": 999 }  # ← Attacker tries to recharge for user 999
Defense (with X-User-Id):

1. Gateway validates JWT token (User A, userId: 4)
2. Gateway extracts userId from JWT: 4
3. Gateway adds header: X-User-Id: 4
4. Recharge Service uses X-User-Id: 4 (ignores request body)
5. Recharge created for User 4 only ✅
Purpose 3: Accessing Own Data

// In RechargeService.getRechargeById()
public RechargeResponse getRechargeById(String rechargeId, Long userId) {
    Recharge recharge = rechargeRepository.findByRechargeId(rechargeId)
            .orElseThrow(() -> new ResourceNotFoundException("Recharge not found"));

    // Security check: User can only access their own recharges
    if (!recharge.getUserId().equals(userId)) {  // ← Uses X-User-Id
        throw new BadRequestException("Unauthorized access to recharge");
    }

    return mapToResponse(recharge);
}
Purpose 4: Feign Client Forwarding

// FeignClientInterceptor forwards X-User-Id to downstream services
String userId = request.getHeader("X-User-Id");
if (userId != null) {
    template.header("X-User-Id", userId);  // ← Forwarded to Operator/Payment Service
}
Why Not Use JWT Directly in Services?

Separation of Concerns: Gateway handles JWT validation, services handle business logic
Performance: Services don't need to validate JWT (expensive operation)
Simplicity: Services just read a header, no JWT library needed
Stateless: Services don't need JWT secret keys
Security Model:

Gateway (Trusted Zone)
  ├─ Validates JWT signature
  ├─ Extracts userId from JWT payload
  ├─ Adds X-User-Id header (cannot be spoofed)
  └─ Forwards to services

Services (Trust Gateway)
  ├─ Read X-User-Id header
  ├─ Use for authorization
  └─ No JWT validation needed
